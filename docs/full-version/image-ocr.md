# Task 4b.1: image and PDF OCR evidence

This delivery slice starts the complete task-4b contract in `conversion-ocr.md`.
It implements image decoding and baseline OCR, not a replacement for office
conversion, isolated archive admission, layout/dewarp/handwriting, specialized
regions or CAD. All remaining ledger requirements and real acceptance gates
remain active.

## Versioned evidence and compatibility

Introduce an explicit new processing profile/payload version for OCR. Preserve
the exact legacy native-v1 serialization and profile hash when reading stored
artifacts; adding default fields to the old model must not make existing encrypted
evidence unreadable. Old processing results stay immutable, and new capability
or toolchain changes require an explicit new run.

OCR text is a transcription of pixels. Do not put it in a field claiming an
original embedded text layer. Distinguish native text and OCR transcription in
typed blocks and source-map spaces. Retain actual word/line locations, confidence,
recognition languages, engine/model identities and original source hash.

All binary/package/model assets that affect output belong to the frozen profile:
Tesseract and image decoder versions, traineddata SHA-256, source code, options,
limits and coordinate-transform policy. Installed native/OCR package adapters,
data and binaries, their selected dependency graph, the Python executable,
standard-library assets and compiled schema runtime are also
fingerprinted. Generated bytecode is excluded only when the runner enforces
source-only execution from interpreter startup: cached or sourceless bytecode,
ZIP imports, site hooks and `.pth` files must not execute outside that identity.
`-B` alone prevents writes and is insufficient to prevent cache reads. The
source-only bootstrap and its execution policy belong to the frozen identity.
Before either interpreter is launched, a non-interactive shell gate checks the
explicit `DOCUMENT_RUNTIME_PYTHON_SHA256` pin against the qualified distribution
build and refuses startup ZIP candidates, including dangling links. This boundary
precedes Python's initial `encodings` import; removing ZIP hooks afterward cannot
protect that import. The current recipe requires a source-based `/usr` runtime,
matching system/venv interpreters and venv `home=/usr/bin`; custom builds must be
qualified separately. Guard tools, their loader dependencies and venv metadata
also belong to the new processing identity.
Capability probing and asset hashing run
outside SQL; a configured but unavailable OCR runtime fails closed. No backend
credentials, user documents or server modules enter the parser-code staging.

## Images, scans and coordinates

Handle JPG/PNG/TIFF/HEIC/BMP/WEBP, all TIFF/HEIC visual frames, scanned PDF pages
and mixed native-text/image PDF content. Bound actual dimensions, frame/page
counts, decoded pixels, text/blocks, output and runtime before large allocations.
Process pages/frames in bounded chunks where a complete document would exceed a
single sandbox's limits; never bypass the package's 20 documents, 50 MB,
1000-page or later token budgets. A cumulative pixel count is not permission to
allocate every frame at once.

Keep native evidence intact when adding OCR. Record crop, scaling, orientation,
rotation and deskew transforms and map OCR locations back to the declared
original coordinate space. Decoder-applied transforms must be identified rather
than silently counted twice. No fabricated PDF pages, original-image coordinates
or exact dewarp mappings. Nonlinear dewarp remains a later task-4b component.

TIFF anchors use the stored frame's encoded dimensions; Pillow's decoder-applied
EXIF rotation/reflection must be recorded once. HEIC declares the decoded visual
frame basis explicitly when container geometry cannot be asserted. Transparent
pixels must be rendered through the frozen white-matte policy, never exposed as
visible hidden RGB text by dropping alpha. New runs select transform policy v3;
older serialized v2 defaults remain readable with their original hashes.

Use actual Tesseract word boxes/confidence, not a fake OCR adapter or generated
answer. Low-confidence or unreadable regions remain pending. Numeric OCR values
require review until a versioned expert-calibrated policy or audited correction
accepts them; synthetic printed fixtures cannot certify numeric accuracy.
Successful text OCR does not establish that handwriting, signatures, diagrams
or other visual regions have been interpreted.

## Execution and storage integration

Extend the verified OS runner and its bounded protocol. CLI input/output uses
private RAM-backed temporary paths generated by the server, not document names.
No network, private folders, application environment or host-parser fallback.
Bound subprocess threads/processes, stdout/stderr and wall time; clean up on
success, cancellation, timeouts and crashes. Do not run OCR in the API process.

Publish OCR evidence through the existing encrypted artifact ownership/fencing
and atomic checkpoint path. Keep tenant/project/source/profile-qualified cache
reuse, current-original binding, append-only attempt history and proof-before-GC.
Retry must preserve healthy work and avoid duplicate committed outputs. Binary
preview persistence/viewer integration is subsequent work; absence of a preview
must not be reported as a completed source viewer.

Expose the versioned evidence via the authenticated nested APIs and update the
client types to distinguish OCR and native source text. Actual tokenization and
external AI permission stay task-5 gates; parsing still grants neither permission
nor ready-to-submit status.

## Configuration and source consumers

`backend/.env.full.example` keeps `APP_DOCUMENT_OCR_MODE=disabled`. Select
`tesseract` explicitly only with a qualified isolated runtime and its frozen
language assets (`rus`, `uzb`, `uzb_cyrl`, `eng`, plus orientation data).
The profile records binaries, library identities and asset hashes, so installing
an executable alone never authorizes a different processing result under an old
profile. The development verification helper forwards configured
`APP_DOCUMENT_OCR_*` values only with `verify --documents`, removes inherited
test-runner settings, and leaves native-only verification without an OCR opt-in.

Frame, raster and cumulative bounds are separate: 12 million source pixels per
frame, 8 million raster pixels per chunk and 2 billion pixels cumulatively by
default. `APP_DOCUMENT_OCR_DOCUMENT_SECONDS=3600` bounds the whole sequential
document; the existing OS runner enforces its own smaller wall/CPU/memory bounds
per chunk. The frozen OCR limits additionally cap cumulative measured CPU at
1800 seconds per document. These safety limits do not certify the PRD's
throughput targets.

Authenticated detail and block responses expose `schema_version="1"|"2"`.
The frontend contract uses a discriminated native/OCR block union; both old
native evidence and new raster evidence keep the original source binding.
Native blocks expose `original_text`, whereas `ocr_word`/`ocr_line` expose
`transcription_text` with `source_map_space="ocr_transcription"`, confidence,
languages, engine and review flags. A TypeScript consumer contract verifies
that reading `original_text` from an OCR block is a compile-time error. It does
not render a source preview or resolve OCR review flags.

Package format metadata uses `ocr_required` for recognized raster formats.
This describes the processing need even with OCR disabled, rather than claiming
that installing a decoder grants processing availability. Original immutable
manifests remain historical inputs; the selected processing profile and measured
inspection/normalization result establish the actual capability for a run.
